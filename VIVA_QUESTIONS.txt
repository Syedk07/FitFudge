Q20. Which database is used in FitFudge, and why is SQLite appropriate for a
     mobile fitness app?

     Topics to prepare:
     SQLite is embedded (no server), zero-configuration, ACID compliant,
     fast for single-user local reads/writes, ideal for offline apps.

Q21. List the seven database tables and explain what each one stores.

     Topics to prepare:
     user_profile, user_account, exercises, workout_templates,
     workout_sessions, workout_set_records, body_measurements — know the
     columns and purpose of each.

Q22. How is the database created and initialised on first launch?

     Topics to prepare:
     openDatabase() with version: 1 and onCreate callback, _onCreate runs
     all seven CREATE TABLE statements. The database file is named
     fitfudge.db and placed at the path returned by getDatabasesPath().

Q23. The user_profile table uses id = 1 as a fixed primary key. Why? What
     does ConflictAlgorithm.replace do when saving the profile?

     Topics to prepare:
     Single-user app, always overwrite the same row, INSERT OR REPLACE
     semantics — deletes the existing row and inserts the new one if the
     primary key conflicts.

Q24. Explain the relationship between workout_sessions and
     workout_set_records. How is referential integrity handled?

     Topics to prepare:
     workout_set_records.sessionId is a FOREIGN KEY referencing
     workout_sessions.id. When a session is deleted, the code manually
     deletes the corresponding set records in deleteSession() because SQLite
     does not enforce CASCADE DELETE by default without PRAGMA
     foreign_keys = ON (which sqflite does not enable automatically).

Q25. How are personal records calculated? Walk through the SQL query used.

     Topics to prepare:
     rawQuery with SELECT exerciseId, MAX(weightKg), MAX(reps),
     MAX(weightKg * reps) AS maxVolumeSet, COUNT(*) FROM
     workout_set_records GROUP BY exerciseId ORDER BY maxWeightKg DESC.
     These are computed on every loadAll() call — they are not stored as a
     separate table.

Q26. The exercise seed data (kExercises) is a compile-time const List in
     exercise_data.dart. On first launch, it is inserted into the exercises
     table. How does the app detect whether seeding has already happened, and
     why is this important?

     Topics to prepare:
     exercisesSeeded() runs SELECT COUNT(*) FROM exercises — if count > 0,
     skip seeding. Without this check, exercises would be duplicated on
     every launch (though conflictAlgorithm: ignore would silently skip
     them, it wastes a batch operation).

Q27. The exerciseIdsJson column in workout_templates stores exercise IDs as a
     comma-separated string, not as a true foreign-key relationship or JSON
     array. What are the drawbacks of this approach?

     Topics to prepare:
     Cannot query exercises by template with SQL JOINs, no referential
     integrity (deleted exercise ID stays in the string), parsing required
     in Dart code, harder to extend (e.g. add per-exercise sets count to
     template). A proper junction table would be more correct.

Q28. How does the app handle nullable body measurement fields such as
     chestCm, waistCm, and armsCm? How are these stored and retrieved from
     SQLite?

     Topics to prepare:
     Dart nullable types (double?), stored as REAL (nullable column) in
     SQLite, retrieved with null check: m['chestCm'] != null ?
     (m['chestCm'] as num).toDouble() : null.

Q29. Walk through exactly what happens from when a user taps "Finish Workout"
     to when the session appears in the History screen.

     Topics to prepare:
     finishWorkout() → timer cancelled → loops through activeExercises,
     only saves sets where isCompleted == true → calculates totalVolume
     (weight * reps for each set) → inserts WorkoutSession → gets sessionId
     → maps all set records with that sessionId → batch inserts
     WorkoutSetRecords → reloads _sessions and _prs from DB →
     notifyListeners() → resets active workout state → UI rebuilds.

Q30. The workout timer in WorkoutProvider uses dart:async Timer. How does it
     work, and what happens to the timer when the user navigates away from the
     active workout screen?

     Topics to prepare:
     Timer.periodic fires every second, increments _elapsedSeconds,
     calls notifyListeners(). The timer lives in the Provider (not the
     Screen widget), so it keeps running even if the screen is popped.
     The active workout banner on HomeScreen continues to show the elapsed
     time. Timer is cancelled in finishWorkout(), cancelWorkout(), and
     dispose().

Q31. The updateSetWeight and updateSetReps methods in WorkoutProvider
     deliberately do NOT call notifyListeners(). Why?

     Topics to prepare:
     Text fields in _SetRow have their own TextEditingController and manage
     their own state locally. Calling notifyListeners() on every keystroke
     would rebuild the entire active workout list, resetting focus and
     causing a poor typing experience. The values are read back on
     finishWorkout().

Q32. How does the exercise search and filtering work in ExerciseProvider?
     What fields are searched?

     Topics to prepare:
     _applyFilters() is called on every search/filter change. Search checks
     name, primaryMuscle, and equipment (all case-insensitive). Separate
     filters for muscle group, difficulty, and equipment can be stacked.
     _filtered is the derived list; _allExercises is the full list from DB.

Q33. How are the Fitness Calculator results displayed on the Dashboard, and
     how do they update when the user changes their profile?

     Topics to prepare:
     DashboardScreen calls FitnessCalculator.calculateMacros(profile)
     directly (pure function, no caching). context.watch<UserProvider>()
     means any profile change triggers a rebuild of DashboardScreen,
     which recalculates macros, BMI, TDEE automatically.

Q34. Explain the Mifflin-St Jeor equation as implemented in FitnessCalculator.
     Why is there a different formula for male, female, and other?

     Topics to prepare:
     Male: 10w + 6.25h - 5a + 5
     Female: 10w + 6.25h - 5a - 161
     Other: average of male and female formulas
     The formula accounts for metabolic differences. "Other" uses an average
     as a pragmatic approximation.

Q35. How does the 1-Rep Max calculator work? What formula is used?

     Topics to prepare:
     Epley formula: weight × (1 + reps / 30). If reps == 1, returns weight
     directly. The screen also shows a training percentages table (60%–95%
     of 1RM). The result updates only when the Calculate button is tapped
     (no live calculation).

Q36. How does the streak calculation work? What is its time complexity, and
     when could it become a performance concern?

     Topics to prepare:
     The dashboardStats getter iterates up to 365 days backward from today.
     For each day, it searches through the entire _sessions list. This is
     O(365 × N) where N is the number of sessions. With hundreds of
     sessions this is still fast, but it runs every time the dashboard
     rebuilds. A more efficient approach would sort sessions and use a
     set of date strings.

Q47. The splash screen loads all four providers simultaneously using
     Future.wait(). What is the advantage of this over loading them
     sequentially, and what is the potential downside?

     Topics to prepare:
     Parallel loading is faster (total time = slowest task, not the sum).
     Downside: if the DB is busy, concurrent reads could block each other.
     In practice with SQLite and read-only operations this is fine, but
     concurrent writes would need serialisation.

     Topics to prepare:
     All sessions loaded into memory at once, list could grow large,
     ListView.builder is efficient (only renders visible items) but the
     underlying list is still in RAM. Solution: pagination with LIMIT/OFFSET
     in SQL, lazy loading, or date-range filtering.

Q55. The Singleton pattern in DatabaseHelper lazily initialises the database
     using the null-coalescing assignment operator (_db ??= ...). What would
     happen if two async operations both called the database getter
     simultaneously before _db was initialised?

     Topics to prepare:
     Dart's event loop is single-threaded, so ??= is effectively atomic
     within a single isolate. However, two awaiting calls to get database
     could both pass the null check before _initDatabase() completes,
     causing two database open operations. A proper fix uses a Completer
     or an initialization lock.

Q56. The exerciseIdsJson field in WorkoutTemplate stores exercise IDs as a
     comma-separated string. How is this value parsed back into a List when
     starting a workout, and what could go wrong?

     Topics to prepare:
     The value is split by comma in the WorkoutTemplates screen to look up
     each Exercise by ID via ExerciseProvider.getById(). Problems: if an
     ID contains a comma, parsing breaks; if an exercise was deleted from
     the DB after the template was created, getById() returns null and must
     be handled; leading/trailing spaces need trimming.

Q57. Why does the FitnessCalculator implement its own _log10() function
     instead of using dart:math's log()?

     Topics to prepare:
     dart:math provides log() (natural log). log10(x) = log(x) / log(10).
     The manual implementation hardcodes the divisor 2.302585092994046.
     It also returns 0 for x <= 0 or x == 1 to avoid divide-by-zero in the
     US Navy body fat formula — but this silently hides invalid measurement
     inputs rather than surfacing them as errors.

============================================================
  PROJECT-SPECIFIC WEAK POINTS TO PREPARE
============================================================

  These are areas in the actual implementation where a technical interviewer
  is likely to probe with follow-up questions.

  1.  NO REAL AUTHENTICATION
      UserAccount has hardcoded mock fields (userId = 'usr_ff_73921',
      email = 'athlete@fitfudge.com'). There is no login/register screen,
      no password hashing, and no token management. Be ready to explain
      what would need to change.

  2.  NO AUTOMATED TESTS
      widget_test.dart contains only a placeholder test (expect(true,
      isTrue)). No unit tests for FitnessCalculator, no widget tests for
      screens, no integration tests. Be ready to describe what you would
      test first.

  3.  MANUAL CASCADE DELETE (NO FOREIGN KEY ENFORCEMENT)
      SQLite foreign keys are not enabled (PRAGMA foreign_keys = ON is not
      called). Referential integrity between workout_sessions and
      workout_set_records is maintained manually in deleteSession(). A bug
      here would leave orphaned rows.

  4.  exerciseIdsJson AS COMMA-SEPARATED STRING
      This is not a proper relational design. It cannot be queried with
      SQL JOINs, has no referential integrity, and is brittle to parse.
      A junction table (template_exercises) would be the correct approach.

  5.  IN-PROGRESS WORKOUT NOT PERSISTED
      If the OS kills the app during an active workout, all set data is
      lost. There is no draft/checkpoint save mechanism for in-progress
      sessions.

  6.  STREAK ALGORITHM EFFICIENCY
      The streak calculation is O(365 × N sessions) and runs inside a
      computed getter called on every Dashboard rebuild. With a large
      history this could cause visible jank.

  7.  NO INPUT RANGE VALIDATION
      The profile edit sheet only checks for parse failure (null). Values
      like age = -1, height = 0, or weight = 9999 are accepted and passed
      to FitnessCalculator, potentially producing division by zero (BMI)
      or nonsensical results.

  8.  SINGLETON DATABASE INITIALISATION RACE CONDITION
      The lazy _db ??= pattern in DatabaseHelper is safe in practice due
      to Dart's single-threaded event loop, but two concurrent awaiting
      callers reaching the getter before initialisation completes could
      both trigger _initDatabase(). Be prepared to discuss this.

  9.  _log10() MANUAL IMPLEMENTATION
      The custom log base-10 function in FitnessCalculator does not use
      dart:math. It silently returns 0 for invalid inputs (x <= 0),
      which hides bad measurement data rather than surfacing it.

  10. NO DATA BACKUP OR EXPORT
      All data is in a local SQLite file. There is no export feature, no
      cloud backup, and no migration strategy. Uninstalling the app or
      switching devices permanently loses all history.
