PROJECT VIVA & TECHNICAL INTERVIEW QUESTIONS
FitFudge — Elite Athletic Training & Performance System

Language:      Dart / Flutter (SDK >= 3.0)
Platform:      Android, iOS, Web, Windows, macOS, Linux
Architecture:  Provider + ChangeNotifier (MVVM-style)
Database:      SQLite via sqflite (local, on-device)
Key Libraries: provider ^6.1.2, sqflite ^2.3.3, path ^1.9.0, intl ^0.19.0
Deployment:    Local only (no cloud hosting; all data stored on-device)
Auth:          None (mock UserAccount; no real authentication)

----------------------------------------------------------------
SECTION 1: PROJECT OVERVIEW
----------------------------------------------------------------

Q1. What is FitFudge and what problem does it solve?
A: FitFudge is a local-first cross-platform fitness tracking app that lets athletes log workouts, track body measurements, and calculate nutrition targets entirely offline, with no account or internet connection required.

Q2. Who are the intended users of FitFudge, and what are the main things they can do inside the app?
A: The target users are fitness enthusiasts and athletes who can create workout templates, run and log active workout sessions, browse an exercise library, track body measurements, and view calculated macros and personal records.

Q3. FitFudge stores all data locally on the device. What are the advantages of this design choice, and what are the trade-offs?
A: Advantages include full offline access, user privacy, and zero server costs. The trade-offs are that data is lost if the app is uninstalled, there is no cross-device sync, and no backup exists unless the user manually exports it.

Q4. The app has five main screens. Walk through the user journey from opening the app to completing and reviewing a workout.
A: The SplashScreen loads all data, then the user picks a template in Workouts, taps Start, logs sets on the Active Workout screen, taps Finish to save, and then reviews the session in the History screen along with updated personal records on the Dashboard.

Q5. What are the current limitations of FitFudge that you would address in a future version?
A: The main limitations are no real authentication, no cloud sync or data backup, no progress charts, no rest timer, no push notifications, and the test suite is only a placeholder.

Q6. The UserAccount model stores membershipTier, userId, and authProvider but with hardcoded mock values. Why was this structure included if authentication is not implemented?
A: The schema was designed to be forward-compatible, so that real authentication (e.g. Firebase Auth) can be integrated later without a database migration — the table and columns already exist.

SECTION 2: TECHNOLOGY STACK
----------------------------------------------------------------

Q7. Why was Flutter and Dart chosen instead of building separate native Android and iOS apps?
A: Flutter allows a single Dart codebase to produce native-quality apps on Android, iOS, web, and desktop, with hot reload for fast development and a rich widget system that avoids building the UI twice.

Q8. What version constraints does this project have and where are they defined?
A: They are defined in pubspec.yaml; the Dart SDK is constrained to >=3.0.0 <4.0.0, and each package uses the caret operator (^) meaning "accept compatible minor/patch upgrades".

Q9. What is the role of each external package — provider, sqflite, path, intl?
A: provider manages reactive state via ChangeNotifier; sqflite is the Flutter SQLite wrapper for local persistence; path constructs the cross-platform file path to the database file; intl formats timestamps into human-readable date strings.

Q10. Give a specific example of where the intl package is used.
A: DateFormat('EEE, MMM d').format(DateTime.fromMillisecondsSinceEpoch(session.startTime)) is used in dashboard_screen.dart and workout_history_screen.dart to display dates like "Mon, Sep 28".

Q11. Why is the path package needed alongside sqflite? Could sqflite work without it?
A: sqflite's getDatabasesPath() returns the OS-specific directory, and join() from path safely concatenates it with 'fitfudge.db' across all platforms — without it you would need to hardcode platform-specific separators.

Q12. flutter_lints is listed under dev_dependencies. What is it for and why is it separate from regular dependencies?
A: flutter_lints provides the official Flutter lint rules for static analysis (run via flutter analyze); dev_dependencies are only used during development and are never bundled into the release build.

SECTION 3: ARCHITECTURE
----------------------------------------------------------------

Q13. Describe the overall architecture of FitFudge.
A: The code is split into three layers inside lib/: data (models, database, calculator, exercise seed data), providers (state management via ChangeNotifier), and ui (screens, theme, reusable widgets) — a clean MVVM-style separation.

Q14. What is the Provider pattern and why was it chosen over alternatives like Bloc or Riverpod?
A: Provider wraps Flutter's InheritedWidget; a ChangeNotifier class holds state and calls notifyListeners() to rebuild dependent widgets. It was chosen because it is the Flutter-team-recommended solution for mid-size apps and requires minimal boilerplate.

Q15. There are four providers. Why are they kept separate rather than combined into one?
A: Each provider has a single responsibility, so a profile change only rebuilds widgets watching UserProvider and does not needlessly rebuild the workout history or exercise list — improving performance and keeping code maintainable.

Q16. How does data flow from the SQLite database to the UI? Trace the path for workout sessions.
A: SplashScreen calls WorkoutProvider.loadAll() → DatabaseHelper.getAllSessions() queries workout_sessions → returns List<WorkoutSession> stored in _sessions → UI uses context.watch<WorkoutProvider>() and rebuilds whenever notifyListeners() is called.

Q17. The DatabaseHelper uses a singleton pattern. What is a singleton and why is it appropriate here?
A: A singleton is a class that allows only one instance, achieved here via a private constructor and a static final instance field — it ensures only one Database connection object is ever opened to the same SQLite file.

Q18. How does the SplashScreen load all data, and what happens if one of the loads fails?
A: It calls Future.wait([userProvider.loadUser(), exerciseProvider.loadExercises(), workoutProvider.loadAll(), bodyProvider.loadMeasurements()]) in parallel with a minimum 1.5 s delay; if any Future throws an error there is no try/catch, so the splash screen would freeze.

Q19. Why does HomeScreen use a Stack for the active workout banner rather than placing it in the AppBar or BottomNavigationBar?
A: A Stack with a Positioned widget lets the banner float precisely above the nav bar at a calculated offset (kBottomNavigationBarHeight + MediaQuery padding), accounting for the iPhone home indicator without interfering with navigation.

SECTION 4: DATABASE
----------------------------------------------------------------

Q20. Which database is used and why is SQLite appropriate for a mobile fitness app?
A: SQLite is used via the sqflite package; it is embedded (no server needed), zero-configuration, ACID-compliant, and fast for single-user local reads and writes — perfect for an offline-first app.

Q21. List the seven database tables and what each one stores.
A: user_profile (personal stats), user_account (mock auth info), exercises (seeded exercise library), workout_templates (saved workout plans), workout_sessions (completed session summaries), workout_set_records (individual sets per session), body_measurements (weight and body measurements over time).

Q22. How is the database created and initialised on first launch?
A: openDatabase() is called with version: 1 and an onCreate callback that executes all seven CREATE TABLE SQL statements; the file is named fitfudge.db and stored at the path returned by getDatabasesPath().

Q23. The user_profile table uses a fixed primary key of id = 1. Why, and what does ConflictAlgorithm.replace do?
A: Because it is a single-user app there is always exactly one profile row; ConflictAlgorithm.replace implements INSERT OR REPLACE semantics — if a row with id = 1 already exists it is deleted and the new row is inserted, effectively updating it.

Q24. Explain the relationship between workout_sessions and workout_set_records and how referential integrity is handled.
A: workout_set_records has a sessionId foreign key referencing workout_sessions.id; when a session is deleted, deleteSession() manually deletes the matching set records because sqflite does not enable PRAGMA foreign_keys = ON by default, so CASCADE DELETE does not work automatically.

Q25. How are personal records calculated? Walk through the SQL query.
A: A rawQuery uses SELECT exerciseId, MAX(weightKg), MAX(reps), MAX(weightKg * reps), COUNT(*) FROM workout_set_records GROUP BY exerciseId ORDER BY maxWeightKg DESC — they are computed dynamically on every loadAll() call and not stored in a separate table.

Q26. How does the app detect whether exercise seeding has already happened and why does this matter?
A: exercisesSeeded() runs SELECT COUNT(*) FROM exercises; if the count is greater than zero, the batch insert of kExercises is skipped, preventing redundant DB writes on every app launch.

Q27. What are the drawbacks of storing exerciseIdsJson as a comma-separated string in workout_templates?
A: You cannot JOIN exercises and templates in SQL, there is no referential integrity (a deleted exercise ID persists silently in the string), and Dart-side parsing is fragile — a proper junction table (template_exercises) would be the correct relational approach.

Q28. How are nullable body measurement fields handled in Dart and SQLite?
A: The Dart model uses double? (nullable types); SQLite stores them as REAL with no NOT NULL constraint; on retrieval the code checks m['chestCm'] != null before casting to double, returning null if the column was never set.

SECTION 5: CORE FEATURES
----------------------------------------------------------------

Q29. Walk through what happens from tapping "Finish Workout" to the session appearing in History.
A: finishWorkout() cancels the timer, loops through active exercises saving only isCompleted == true sets, calculates totalVolume (weight × reps), inserts a WorkoutSession, re-maps set records with the new sessionId, batch-inserts them, reloads _sessions and _prs from the DB, then calls notifyListeners() to update the UI.

Q30. How does the workout timer work and what happens when the user navigates away from the active workout screen?
A: A Timer.periodic fires every second inside WorkoutProvider, incrementing _elapsedSeconds and calling notifyListeners(); because the timer lives in the provider (not the screen widget) it keeps running after navigation, and the active workout banner on HomeScreen shows the live count.

Q31. Why do updateSetWeight and updateSetReps deliberately NOT call notifyListeners()?
A: Each set row has its own TextEditingController managing text field state locally; calling notifyListeners() on every keystroke would rebuild the entire exercise list, reset keyboard focus, and ruin the typing experience — the values are read back only when finishWorkout() is called.

Q32. How does exercise search and filtering work in ExerciseProvider?
A: Every search or filter change calls _applyFilters(), which filters _allExercises by checking if the query matches the exercise name, primaryMuscle, or equipment (case-insensitive), then applies separate stacked filters for muscle group, difficulty, and equipment, storing the result in _filtered.

Q33. How are Fitness Calculator results displayed on the Dashboard and how do they stay in sync with profile changes?
A: DashboardScreen calls FitnessCalculator.calculateMacros(profile) as a pure function on every build; because it watches UserProvider with context.watch, any profile update triggers a rebuild that automatically recalculates BMI, TDEE, and macros.

Q34. Explain the Mifflin-St Jeor equation as implemented and why there are different formulas per gender.
A: Male: 10w + 6.25h − 5a + 5; Female: 10w + 6.25h − 5a − 161; Other: average of both — the male and female constants reflect physiological metabolic differences, and "Other" uses the midpoint as a pragmatic, inclusive approximation.

Q35. How does the 1-Rep Max calculator work?
A: It uses the Epley formula: 1RM = weight × (1 + reps / 30); if reps == 1 it returns the weight directly; results are shown with a training percentages table (60%–95% of 1RM) and only update when the Calculate button is tapped.

Q36. How does the streak calculation work and when could it become a performance concern?
A: The dashboardStats getter walks backward day-by-day up to 365 days and for each day scans the full _sessions list — O(365 × N); with hundreds of sessions this is still fast, but running inside a computed getter on every Dashboard rebuild could cause jank at large scale.

SECTION 6: SECURITY
----------------------------------------------------------------

Q37. FitFudge has no real authentication. What risks exist and what changes would be needed to add it?
A: Currently any user with physical device access sees all data; to add real auth you would integrate Firebase Auth or a backend API, replace hardcoded userId with a real UID, store tokens in flutter_secure_storage, and add route guards to protect screens.

Q38. Who can access the SQLite database on a real device and what are the security implications?
A: On Android the DB is in the app's private sandbox (/data/data/<package>/databases/) inaccessible to other apps, but a rooted device could expose it; on iOS it sits in the app container; for sensitive data, encrypting with SQLCipher would be the mitigation.

Q39. There is no value-range validation in the profile edit sheet. What problems could this cause?
A: A user entering height = 0 would cause division by zero in the BMI calculation; negative age or extreme weight values would produce nonsensical BMR/macro results; the fix is to add range checks (e.g. age 10–120, height 100–250 cm) before saving.

Q40. No API keys or secrets are stored. What would change if a third-party API like Firebase were added?
A: Keys must never be committed to GitHub; they would be placed in platform-specific config files (google-services.json / GoogleService-Info.plist) which are gitignored, or managed via flutter_dotenv, with tokens stored in flutter_secure_storage at runtime.

SECTION 7: UI, THEME, AND USER EXPERIENCE
----------------------------------------------------------------

Q41. FitFudge uses a single dark theme. How is it enforced and how is light mode prevented?
A: In MaterialApp both theme and darkTheme are set to AppTheme.darkTheme and themeMode is set to ThemeMode.dark, so the OS light/dark preference is ignored and the app always renders the dark brand palette.

Q42. In the Material 3 ColorScheme the gold accent (#CFB595) is mapped to primary, not secondary. Why?
A: In Material 3, ColorScheme.primary drives the colour of interactive widgets — ElevatedButton backgrounds, FABs, checkboxes, and progress indicators — so mapping the visible gold accent to primary means all interactive elements automatically use the brand colour without per-widget overrides.

Q43. How does the app handle the iPhone home indicator safe area in the navigation bar and workout banner?
A: SafeArea(top: false) wraps the BottomNavigationBar to clear the home indicator; the active workout banner uses Positioned with a bottom value of kBottomNavigationBarHeight + MediaQuery.of(context).padding.bottom so it floats exactly above both elements.

Q44. How are muscle groups communicated visually in the exercise library and during an active workout?
A: The muscleGroupColor() function in app_theme.dart maps muscle group names to distinct colours (chest = red, back = blue, legs = green, etc.) which are applied to MuscleChip labels and ExerciseCard icon backgrounds throughout the app.

Q45. widget_test.dart is just a placeholder. How would you write meaningful tests?

Q46. Which parts of FitFudge are easiest and hardest to unit test?

SECTION 9: PERFORMANCE AND SCALABILITY
----------------------------------------------------------------

Q47. What is the advantage of using Future.wait() on the SplashScreen and what is the potential downside?
A: Future.wait runs all four provider loads in parallel so total load time equals the slowest single task rather than their sum; the downside is that SQLite concurrent reads from the same connection could contend, though in practice read-only operations handle this fine.

Q48. What would happen to performance if a user had 1,000+ workout sessions?
A: getAllSessions() loads every session into memory at once; while ListView.builder only renders visible items, the full list stays in RAM and query time grows — pagination with SQL LIMIT/OFFSET or date-range filtering would be needed to keep the app responsive.

Q49. What architectural changes would be required to support multiple users on the same device?
A: Every table that holds personal data (workout_sessions, workout_templates, body_measurements) would need a userId foreign key; a users table and login/logout flow would be added; and all queries would be filtered by the currently logged-in userId.

SECTION 11: REAL-WORLD SCENARIO QUESTIONS
----------------------------------------------------------------

Q51. A user reports that finishing a workout shows nothing in History. How would you investigate?
A: First check whether the user actually tapped the checkmark to mark sets as completed — finishWorkout() only saves sets where isCompleted == true; then verify the session was inserted by checking the DB directly and confirming _sessions is reloaded after the insert.

Q52. The exercise library is empty on iOS but works on Android. How would you debug this?
A: Verify that getDatabasesPath() returns a writable path on iOS, check whether the exercisesSeeded() count query returns the correct result, and confirm the batch insert of kExercises completes without a silent error by adding logging around the insertExercises call.

Q53. The user takes a phone call mid-workout for 10 minutes. What happens to the timer and data?
A: The Timer.periodic in WorkoutProvider keeps running in the background because Dart's isolate is not suspended, so _elapsedSeconds continues incrementing; if the OS kills the app under memory pressure the in-progress set data is lost entirely as there is no draft persistence.

Q54. A user deletes a session. What is removed from the database and could orphaned rows remain?
A: deleteSession() explicitly deletes the row from workout_sessions and all matching rows in workout_set_records; orphaned rows could remain only if a bug skips the second delete, because PRAGMA foreign_keys is not enabled so SQLite will not cascade the delete automatically.

SECTION 12: DEEP TECHNICAL QUESTIONS
----------------------------------------------------------------

Q55. The Singleton uses _db ??= to lazily initialise the database. Could two concurrent callers both trigger initialisation?
A: In theory yes — two awaiting callers could both reach the null check before _initDatabase() resolves, starting two open operations; in practice Dart's single-threaded event loop makes this unlikely, but a Completer-based initialization lock would make it formally safe.

Q56. exerciseIdsJson is a comma-separated string. How is it parsed back into a list and what could go wrong?
A: The string is split on commas and each ID is passed to ExerciseProvider.getById(); if an exercise was deleted after the template was created getById() returns null and must be guarded against, and any trailing spaces in IDs need trimming to avoid lookup failures.

Q57. Why does FitnessCalculator implement its own _log10() instead of using dart:math?
A: It hardcodes the natural-log divisor (2.302585092994046) to convert to base-10 and silently returns 0 for invalid inputs (x <= 0) to avoid crashing the US Navy body fat formula — though importing dart:math and using log(x) / log(10) would be cleaner and more transparent about error handling.

PROJECT-SPECIFIC WEAK POINTS TO PREPARE
----------------------------------------------------------------

  1.  NO REAL AUTHENTICATION — UserAccount fields are hardcoded mocks; no login/register flow exists.
  2.  NO AUTOMATED TESTS — widget_test.dart is a single always-passing placeholder.
  3.  MANUAL CASCADE DELETE — PRAGMA foreign_keys is OFF; referential integrity is maintained by hand.
  4.  exerciseIdsJson COMMA-STRING — not relational; no SQL JOINs possible; fragile to parse.
  5.  IN-PROGRESS WORKOUT NOT PERSISTED — OS kill during workout loses all unsaved set data.
  6.  STREAK ALGORITHM — O(365 × N) computed getter runs on every Dashboard rebuild.
  7.  NO INPUT RANGE VALIDATION — height = 0 causes BMI divide-by-zero; no min/max guards on profile fields.
  8.  SINGLETON INIT RACE — _db ??= is safe in practice but not formally thread-safe without a lock.
  9.  _log10() MANUAL IMPL — silently returns 0 for invalid inputs instead of surfacing errors.
  10. NO DATA BACKUP OR EXPORT — uninstalling the app permanently deletes all training history.
